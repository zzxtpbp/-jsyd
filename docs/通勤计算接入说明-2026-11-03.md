## 统一接口

```js
import { calculateCommuteWorkflow } from './commuteWorkflow.js';
const result = calculateCommuteWorkflow({
  now, baseAlarmAt, arrivalAt, recheckAt, // 带日期的Unix毫秒时间戳
  baseAlarmId, commutePlanId, alarms,    // 基础闹钟和计划的稳定ID
  fixedEnabled, smartEnabled, fixedMinutes, maxAdvance,
  preparation, buffer, extra,          // 0..240整数分钟
  ambientEnabled, ambientOffset,       // 开启时1..60整数分钟
  fallback: '保留基础闹钟',             // 或已开启固定时的“仅按固定模式”
  weather: { triggered, updatedAt, validUntil },
  route: { durationMinutes, updatedAt, validUntil }, // 可为null
});
```

完整可执行示例见 `examples/commuteScenarios.js`。上面的变量由接入方提供，不应直接复制为可运行代码。

- `weather.triggered` 必须是布尔值；未知用 null。概率门槛、实况和预警是否独立触发，仍由三人已经对齐的天气政策统一决定，本次没有另写一套判断。
- 供应商坐标、通勤天气窗口、路线方式必须在上游完成匹配。`durationMinutes` 已是所选交通方式的整数分钟；高德秒数应先检查成功结果再转换，不能将失败、空值当零。
- 时间戳和有效期必须来自真实数据及既定缓存政策；本入口不编 TTL。固定仅使用天气有效期；智能使用天气/路线有效期的交集。
- `recheckAt` 需要明确属于哪一天，必须早于最早可能的铃前环境音。该字段是计划配置，本函数不会安排后台复查。
- 基础闹钟必须已存在、开启、时间与 `baseAlarmAt` 相同；否则不建议写入。每日闹钟应先解析成本次确切日期。
- 建议只用可信的通勤记录调用本入口；账号鉴权和闹钟归属校验应在真实保存服务中再次执行。

## 输出及A/C接入边界

| 输出 | 用途 |
| --- | --- |
| `timing.issues / warnings` | 错误阻断，推荐固定模式是非阻断提示 |
| `fixedCandidate / smartCandidate` | 分别保留两种计算诊断，不只保留赢家 |
| `merged` | 较早有效候选，平手稳定选择固定 |
| `write` | `create / update / noop / keep_existing / blocked` 操作建议，无实际I/O |
| `summary.proposedWakeAt` | 本次计算候选，可能因保存阻断不能应用 |
| `summary.wakeAt` | 可用的最终建议或明确保留的唯一同次旧铃；null时不能显示成0分钟 |
| `summary.gapMinutes` | 按最终时间重算缺口；null代表缺少有效数据，不能改成0 |
| `summary.executionState` | `suggested`或`existing_record`，都不代表设备已同步或必定响铃 |

A：接入设置与诊断展示。C：检查`write`，执行真实且原子的upsert，分配新ID，记录持久化/设备回执后才能向用户声称设置成功。一次计算到保存之间如跨过有效期，应重算。

无新候选时不会删除旧铃。摘要只会在归属、日期、启用状态和唯一性都足够明确时展示旧记录；“未展示”不等于旧铃被删除。

注意：此前保存建议模块中的`patch.gapMinutes`是被选候选本身的诊断。固定胜出时仍应使用`summary.gapMinutes`展示最终通勤缺口，不能拿固定候选的null当“来得及”。本次没有修改旧模块协议。
